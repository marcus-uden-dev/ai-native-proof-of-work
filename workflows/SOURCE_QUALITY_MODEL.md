# Source Quality Model

Last updated: 2026-05-08  
Status: Initial version

## Purpose

Filter research and workflow inspiration so the repository does not become a hype archive.

## Quality Criteria

| Criterion | Question | Preferred Answer |
|---|---|---|
| Primary source | Is it from the builder, company, researcher, or original documentation? | Yes |
| Reproducible | Can it be tested or implemented? | Yes |
| Practical | Can it change a workflow or decision? | Yes |
| Relevant | Does it apply to Marcus’s projects? | High |
| Low-hype | Are claims bounded and specific? | Yes |
| Evidence-backed | Are examples, code, screenshots, docs, or metrics provided? | Yes |

## Source Categories

| Category | Handling |
|---|---|
| Primary documentation | High trust, still verify relevance |
| Builder evidence | Good if concrete |
| Secondhand commentary | Use cautiously |
| Viral AI posts | Treat as low trust unless reproducible |
| Content farms | Reject unless unusually specific and verifiable |

## Promotion Rule

Only high-signal sources should become strategy changes, architecture changes, scheduled tasks, skills, or repo instructions.
